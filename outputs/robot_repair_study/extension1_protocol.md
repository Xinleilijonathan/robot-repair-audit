# Extension 1: candidate-population audit (frozen protocol)

Frozen November 15, 2026, before any extension rollout. The files are SHA-256 hashed in `extension1_frozen_hashes.json` before launch. This extension was designed **after** the single-context audit results were known, and it is reported as an add-on. It does not replace or amend that audit. Like the first audit, it was designed by Claude.

## 1. Purpose

The first audit tested two candidates, so its gate comparison rested on two committed decisions. This extension evaluates a *population* of candidate edits from the same bounded interface under the same budget-matched gates and a freshly drawn audit.

**Questions:**

- **Q1.** Among candidates that improve the target neighbourhood on the audit, what fraction lose at least one old success?
- **Q2.** How often do old losses come with offsetting old gains? How often do aggregate and zero-loss admission disagree, both in the committed decisions and across resampled validation draws?
- **Q3.** Per gate:
  - how many candidates it admits;
  - how many admitted candidates have audit losses, and how many losses in total;
  - how many useful candidates it rejects, under each pre-declared objective.
- **Q4.** Do A's and B's audit outcomes replicate on an independent scene draw?

## 2. Candidates

- **Assistant candidates.** `candidate_a` (`{"lift_height": 0.20}`) and `candidate_b` (`{"position_tolerance": 0.025}`), unchanged from the first audit.
- **Random candidates `r01`–`r24`.** These are generated by `make_random_proposals.py` with seed 20261119:
  - The number of edited parameters is k ∈ {1, 2}, with equal probability.
  - The edited parameters are chosen uniformly without replacement from the six-parameter interface.
  - Each new value is drawn uniformly within the runner's existing bounds and rounded to 3 decimals:

    | Parameter | Bounds |
    |---|---|
    | approach_height | 0.05–0.40 m |
    | lift_height | 0.10–0.40 m |
    | position_tolerance | 0.005–0.035 m |
    | grasp_position_tolerance | 0.005–0.035 m |
    | stability_duration | 0.05–0.50 s |
    | gripper_dwell | 0.10–1.00 s |

  - Stock Franka values: approach 0.30, lift 0.30, position tolerance 0.015, grasp tolerance 0.015, stability 0.10 s, dwell 0.20 s.
- **What the random candidates are.** They form a seeded proposal distribution, not an agent, and they are not tuned toward the target. They stress-test the gates with a fixed population. No result about agent or proposer quality follows from them.

## 3. Scenes (`make_extension_manifest.py`, seed 20261118)

- **Populations.** Identical definitions to the first audit:
  - target neighbourhood: r ~ U[0.79, 0.81] m and a ~ U[−62°, −58°];
  - old workspace: r ~ U[0.35, 0.85] m and a ~ U[−60°, 60°], excluding r ∈ [0.77, 0.83] with a ∈ [−64°, −56°].
- **Validation draw.** 12 target (`vt01–vt12`) and 8 old (`vo01–vo08`) scenes.
- **Audit draw.** 30 target (`at001–at030`) and 90 old (`ao001–ao090`) scenes.
- **Execution.** One reset per scene. Each manifest has one shuffled execution order, shared by all configurations.
- **Sizes.** The audit is smaller than the first audit's 40 + 120 so that the 27 configurations fit an overnight run. At roughly 90 parent old successes, the Wilson half-width for a 5% conditional loss rate is about ±5 percentage points.

## 4. Gates and objectives

These are identical to the first audit and use the unchanged, hash-frozen `audit_gates.py` and `analyze_audit.py`.

**Gates:**
- **Aggregate and preservation** use `vt01–vt04` plus `vo01–vo08` (24 rollouts).
- **Target-only** uses `vt01–vt12` (24 rollouts).
- **Frozen** always keeps the parent.
- Parent rollouts are shared between candidates; exact cross-process replay was established in the pilot and in the first audit.
- **Delivered controller:** among admitted candidates, the one with the most candidate successes on that gate's own evidence; ties go to the earliest in queue order (A, B, r01, …).

**Useful update** (audit-measured, declared before any extension rollout):
- *Aggregate objective:* target net > 0 and old net ≥ 0.
- *Preservation objective:* target net > 0 and zero old losses.
- *Secondary:* conditional loss ≤ 5%.

## 5. Analyses

**Primary** (`analyze_audit.py`, then `analyze_population.py`):

- **Per candidate:**
  - all paired cells;
  - target and old success;
  - conditional loss with a Wilson 95% interval;
  - usefulness under each objective;
  - committed gate decisions;
  - resampled admission probabilities (5,000 draws, seed 20261116).
- **Population counts:**
  - candidates that improve the target;
  - of those, candidates with at least one old loss (Q1);
  - candidates with both old gains and old losses, and with gains ≥ losses > 0 (Q2);
  - committed aggregate-vs-preservation disagreements;
  - the mean and maximum resampled disagreement probability (Q2).
- **Per gate:** admissions, admitted candidates with audit losses, total audit losses among admitted candidates, admitted-and-useful and missed-useful counts under each objective, and the delivered controller (Q3).
- **Replication:** A and B on the new draw, compared descriptively with the first audit (Q4).

**Secondary** (descriptive): placement-margin shift, approximate tolerance sensitivity, a figure of candidates by audit target gain against old losses, and the parent repeat check at the end of the queue.

**Uncertainty.** Candidates are draws from a fixed proposal distribution, and scenes are draws from fixed populations. Population fractions get Wilson intervals over candidates. These describe this proposal distribution, robot, task and context only.

## 6. Execution (`work/run_extension1.ps1`)

**Order:**

1. Validation batches: parent, A, B, r01–r24 (27 × 20 rollouts).
2. `audit_gates.py` writes `results/ext1/audit_gate_decisions.json`.
3. Audit batches: parent, A, B, r01–r24 (27 × 120 rollouts).
4. Validation parent repeat (20 rollouts).

That is 3,800 rollouts in total. At the first audit's measured rate of ~9 rollouts per minute, plus process startups, the estimate is 7–9 hours serial.

**Launch and failure handling:**

- **Launcher.** `work/launch_isaac_ps51_timeout.ps1`: the amendment-1 launcher plus a wall-clock timeout of 40 minutes per validation batch and 150 minutes per audit batch. A timed-out process is killed and recorded as an infrastructure failure.
- **Failed batch.** A batch that exits nonzero, times out or is incomplete has its folder renamed to `failed<n>_<name>`, with partial data preserved. It is then rerun *whole*, because outcomes depend on the full ordered sequence. There is one retry per batch.
- **Repeated failure.** A candidate whose validation fails twice is recorded as an infrastructure failure and excluded from the gates; it retains the parent. A candidate whose audit fails twice is excluded from the analysis and reported.
- **Ordering guarantee.** No candidate result triggers any change. Gate decisions are committed only after all validation batches, and before any audit batch.
- **Resuming.** The queue can resume: on restart it skips batches already complete (by folder count and ledger) and reruns incomplete ones under the rename rule. It never overwrites.
- **Keeping the machine awake.** While running, the queue process holds a Windows `SetThreadExecutionState(ES_CONTINUOUS | ES_SYSTEM_REQUIRED)` request, so the machine does not idle-sleep. No system setting is changed. A closed lid or manual sleep still suspends the run.
